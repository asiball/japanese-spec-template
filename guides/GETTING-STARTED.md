# GETTING-STARTED — Markdown に不慣れな方向けの入門

このリポジトリは、Markdown で書いた原稿をきれいな体裁の PDF 仕様書に変換するテンプレートです。この文書は、Markdown を初めて使う方(PM・品質保証担当など)向けに、最初の一歩をまとめたものです。

体裁(フォント・色・レイアウト)は書かなくてかまいません。すべて自動で整います。あなたが書くのは「文章の構造」だけです。

## まず見本をコピーする

ゼロから書き始めるより、動く見本を書き換えていく方が簡単です。見本は `examples/` にあります。

- 1 つのファイルにまとめて書く場合: `examples/wareki-api-spec.md`
- 章ごとにファイルを分ける場合: `examples/sample-spec`(フォルダごと)

自分の原稿は `docs/` に置きます。

```sh
# 単一ファイルで始める場合
cp examples/wareki-api-spec.md docs/my-spec.md

# 章ごとにファイルを分ける場合
cp -r examples/sample-spec docs/my-spec
```

ファイル名は半角英数字とハイフンにしてください(例: `my-spec.md`)。日本語のファイル名は避けます。

章分割の仕組み(どのファイルが何章になるか)は [README](../README.md) の「章別ファイル分割」を参照してください。

## 表紙の情報を書く(YAML メタデータ)

ファイルの先頭にある `---` で挟まれた部分が、表紙に載る情報です。

```yaml
---
title: "在庫管理API 仕様書"
version: "1.0"
date: "2026-08-01"
author: "山田太郎"
organization: "株式会社サンプル"
---
```

`title` は必須です(ないとビルドが止まります)。章分割の場合、この部分は **`00-meta.md` にだけ**書きます。ほかの章ファイルに書くと壊れるので注意してください。

## 見出しは番号が自動で付く

`#` の数で章・節・項が決まり、番号は自動で振られます。

```markdown
# はじめに          ← 「1 はじめに」になる(章。自動で改ページ)
## 目的             ← 「1.1 目的」になる(節)
### 前提条件        ← 「1.1.1 前提条件」になる(項)
```

**自分で番号を書かないでください**。`# 1. はじめに` と書くと番号が二重になるため、ビルド前の検査がエラーで止まります。

## 表・コード・図・脚注の最小例

**表**は縦棒で区切って書きます。直後の行に `: 〜` と書くとキャプション(表タイトル)になります。

```markdown
| 項目 | 内容 |
|---|---|
| 対応OS | Linux、Windows |
| 依存 | なし |

: 対応環境一覧
```

**コード**は 3 つのバッククォートで挟みます。言語名を書くと色分けされます。

````markdown
```python
print("hello")
```
````

**図**(画像)は `assets/images/` に置き、次のように参照します。先頭の `/` を忘れないでください。

```markdown
![システムの構成図](/assets/images/system-overview.png){width=70%}
```

シーケンス図などをテキストから自動生成する仕組み(PlantUML)もあります。詳細は [WRITING.md](WRITING.md) の「図の挿入」を参照してください。

**脚注**は本文に `[^1]` と書き、どこか(通常は文書の末尾)に中身を書きます。

```markdown
本機能は申請が必要である[^1]。

[^1]: 申請窓口は情報システム部。
```

## 改訂履歴が長くなったら別ファイルに

改訂履歴は専用ファイルに表として書けます。単一ファイルなら `docs/my-spec.revisions.md`、章分割なら `docs/my-spec/revisions.md` という名前で置くだけで、自動で表紙の次のページに反映されます。改訂のたびに 1 行足すだけです。

```markdown
| 版数 | 日付 | 作成者 | 改訂内容 |
|---|---|---|---|
| 1.0 | 2026-08-01 | 山田太郎 | 初版作成 |
| 1.1 | 2026-08-15 | 鈴木花子 | 3.2 節の表記を修正 |
```

## PDF を作る

Docker と make が使える環境なら、次の 1 コマンドで PDF ができます(初回だけ数分かかります)。

```sh
make pdf SRC=docs/my-spec.md    # 章分割なら make pdf SRC=docs/my-spec
```

できあがりは `build/my-spec.pdf` です。

手元に Docker がない場合は、次のどちらかで PDF を入手できます。

- 原稿を GitHub に push(アップロード)する。自動ビルド(CI)が走り、PDF がワークフローのアーティファクトからダウンロードできます。
- 開発メンバーにビルドを依頼する。

## やってはいけないこと

- **見た目の指定を書かない**。フォント・色・文字サイズなどの指定は不要で、書いても反映されません。体裁はテンプレートが自動で整えます。
- **見出しに番号を書かない**。番号は自動で付きます。手で書くと二重になります。
- **空白を並べて位置を合わせない**。Word のような字下げ調整はできません。一覧には表や箇条書きを使います。
